## Context

业务系统在关键事件发生时需调用外部供应商 HTTPS API 通知，但各供应商地址/格式/鉴权/签名各异，且业务方不关心返回值、只求可靠送达。本变更建设一个出站通知可靠投递网关（适配中心模式），把可靠投递与供应商对接知识收敛到平台一层。

完整探讨与逐项取舍论证见仓库 `docs/方案决策记录.md` 与 `docs/需求分析.md`；本文件提炼为实现层设计。约束：第一版（MVP），允许使用开源中间件但优先控复杂度，关注工程判断与边界而非功能齐全。

**实现技术栈（约束）**：Go + **Echo 框架**（HTTP 接入层）+ SQLite（`modernc.org/sqlite`，兼作投递队列）+ 进程内 MQ（状态事件分发替身）+ 本地加密配置/环境变量（凭证后端替身）。详见 `openspec/project.md`。

## Goals / Non-Goals

**Goals:**
- 提供 at-least-once 的可靠出站投递，业务方 fire-and-forget。
- 把供应商对接（模板、凭证、鉴权/签名）收敛为平台能力。
- 在外部失败/长期不可用时具备退避、熔断隔离、死信兜底与重放。
- 提供状态可查（运维 + 业务方）与状态事件分发，且不丢事件、不拖垮投递吞吐。
- v1 主动控复杂度：能用现有 DB/简单机制解决的不引入重型中间件。

**Non-Goals:**
- 不解析外部 API 业务语义（只认 HTTP 2xx）。
- 不提供 exactly-once、不保证有序投递。
- 不做请求体转换/编排 DSL；v1 不引入模板/脚本引擎做请求组装（用代码适配类）。
- 不替业务方解决其本地事务与提交的原子性（属业务侧 outbox）。
- 不在 v1 做配置中心 UI/审批流、不上 Vault、不上 Kafka 做投递队列。

## Decisions

### D1：适配中心模式（而非透明中继）
网关存供应商配置，业务方提交 `type + params`，由网关组装请求。**理由**：收敛对接知识到平台一层（中台定位）。**代价**：新增组装层与配置治理；通过把复杂度关在组装层、保持投递内核与适配模式解耦来管理。**备选**：透明中继（业务方传完整请求）更简单但对接知识分散在各业务系统。

### D2：接收时校验 + 投递时由适配类组装（v1 不引入模板、不冻结请求）
v1 不引入模板引擎。接收时调用供应商适配类做必须参数 fail-fast 校验、存储原始 `params`；投递时由适配类据 `params` 组装请求并验签。复盘性由适配类的日志留存（记录实际发出的请求/响应）承接；死信重放用保留的 `params` + 最新适配类重建。**理由**：与 D4 的"代码适配类"同一条路且更彻底，避免引入模板引擎与冻结列、也避免"模板组装"与"代码验签"割裂。**代价**：每接入一个供应商都需一个适配类（简单供应商薄层继承基础类），放弃纯配置零代码接入。**备选（前一版决策，已简化掉）**：`{{var}}` 模板 + 提交时冻结业务骨架——可复盘但需引入模板引擎与冻结存储，且与代码验签两套机制并存。

### D3：DB 表当队列 + 租约 + reaper 折叠 + 领取即计数
v1 用关系型数据库表当投递队列，轮询 + 带条件原子 UPDATE 抢占租约领取；领取查询直接纳入"过期租约的 DELIVERING"，无需独立 reaper 进程；`attempts` 在领取时即 +1。固定租约（> HTTP 硬超时 + 余量，如 30s），单任务有界故不做心跳续租。`next_attempt_at <= now()` 天然实现延迟队列。**理由**：v1 量级够用、可调试性强；租约兜住 worker 崩溃；领取即计数防毒丸无限循环。**备选**：直接上 Kafka（v1 过重）、Redis 分布式锁（见 D-Rejected）。

### D4：每供应商一个适配类，公共能力下沉基础类；凭证晚绑定 + sops
抽象 `SupplierAdapter` 接口，每供应商一个实现类，承载该供应商的必须参数校验、请求组装 + 验签、响应处理与日志留存；公共能力（通用校验、日志、请求脚手架）下沉基础实现类。配置只存 `secret_ref`，投递时由 resolver 解析（v1 后端用 sops 加密配置文件）供适配类使用。适配类只负责对接，传输/重试/租约/2xx 判定归通用 worker。**理由**：各供应商对接（尤其验签）高度异构，靠代码多态比配置 schema 更通用、可用供应商测试向量单测；公共能力沉淀基础类降低重复。**备选**：配置驱动通用签名/模板引擎（越兜越大、漏抽象）。

### D5：状态回查 = 只读拉取 + MQ outbox 分发 + 分层保留
状态变更同事务写 `notification_event`（兼作状态历史与 MQ outbox）。业务方双通道：只读拉取（粗三态默认、detail 受控）+ MQ 事件订阅（pub/sub 扇出，不反向耦合）。MQ 仅用于状态分发，投递队列仍是 DB。终态迁出热表入归档表（领取查询只扫非终态），归档表 v1 暂不清理、长期由离线 Hive 承接。**理由**：pub/sub 比逐个 webhook 推送更解耦（webhook 会让我方递归造可靠投递）；outbox 保证不丢事件且 MQ 非阻塞依赖。**备选**：webhook 推送（递归套娃）、仅运维可查（业务方无法自助对账）。

### D-Rejected：不引入 Redis 分布式锁做任务领取
领取重复已由 DB 条件 UPDATE 原子解决；处理重复（TTL 期间未完成）中 Redis 锁与租约是同种失效、且外部 API 无法校验 fencing token，补不齐 → 唯一解是 at-least-once + 下游幂等。Redis 锁在此只增组件不增保证。Redis 真正该上的时机是作为队列本身（吞吐瓶颈时替换 DB 当队列），非叠锁。

## Risks / Trade-offs

- **DB 当队列的吞吐上限** → 热点行争用/轮询延迟出现时，按演进路线把投递队列替换为 MQ；`(status, next_attempt_at)` 复合索引 + 轮询抖动 + 中等批量领取缓解。
- **at-least-once 带来重复投递** → 下游须幂等（或我方携带幂等键）；这是设计上接受的语义。
- **每供应商一个适配类 = 每接入一个供应商需改代码发版**（放弃纯配置零代码接入）→ 公共能力下沉基础类，简单供应商仅薄层继承；以 v1 简单直接换取后续灵活，待供应商数量大时可再评估是否引入配置化接入。
- **不冻结请求、改由日志留存复盘** → 适配类 MUST 完整留存实际发出的请求与响应，否则丧失复盘能力。
- **v1 引入 MQ（状态分发）增加运维面** → 用 outbox 让 MQ 成为非阻塞下游，MQ 未就绪时查询仍可用。
- **归档表"暂不清理"无界增长** → 以离线 Hive 长期承接；待离线同步建好后归档表可设上限。
- **sops 轮换需重新部署/重载** → resolver 抽象已留好，轮换频繁时换 Vault（热更新）零侵入。
- **401/403 直接进死信可能误判临时性凭证问题** → v1 静态 key 下 401/403 多为配置错；将来 OAuth 适配类内部做"刷新一次再试"。

## Migration Plan

全新服务，无存量迁移。部署顺序：建表（notification 热表/归档表、notification_event、supplier_config）→ 配置首批供应商（含 secret_ref 与 sops 凭证）→ 上线接收 API 与投递 worker → 接入 MQ 状态分发（可后置，outbox 先行）→ 配置 DEAD 告警与运维查询/重放。回滚：投递 worker 与接收层可独立停启；未投递通知留存于 DB，恢复后继续。

## Open Questions

- MQ 选型（RocketMQ / Kafka / 其他）与 topic 划分。
- 归档迁移触发方式（定时任务 vs 状态流转时同步迁移）与离线 Hive 同步管道。
- 幂等键作用域与冲突返回语义（同 key 重复提交返回已有 id 还是报错）。
- 单供应商熔断/并发隔离的具体参数（阈值、半开探测、每供应商并发上限）。
