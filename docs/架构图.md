# API 通知系统 · 总体架构图

> 反映[简化后设计](./需求分析.md)：每供应商一个适配类、v1 不引入模板引擎、DB 当队列 + 租约、MQ 仅做状态事件分发。
> 作为总体指导，后续 tasks 应与这三张图对齐。关联：[需求分析.md](./需求分析.md)、[方案决策记录.md](./方案决策记录.md)。

## 一、分层架构

```
┌────────────────────────────────────────────────────────────────────────────┐
│ 调用方 / 消费方                                                              │
│   业务系统(提交方)        业务系统(订阅方)        运维 / 平台                 │
└────┬─────────────────────────┬────────────────────────┬─────────────────────┘
     │ 提交 / 凭追踪ID查询      │ 订阅状态事件(MQ)        │ 查询 / 列死信 / 重放
     ▼                         ▼                        ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ ① 接入层 (API)                                                               │
│   提交 API   │   业务方只读查询 API(粗三态默认 / detail 受控)   │  运维 API   │
└────┬───────────────────────────────────────────────────────────┬────────────┘
     ▼                                                            ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ ② 应用层 (核心服务)                                                          │
│   接收服务            投递 worker            兜底 & 重放        可观测        │
│   · 幂等去重          · 租约领取(+attempts)   · 失败分类         · 状态查询    │
│   · 适配类校验        · 组装+验签+发送        · 熔断/隔离        · 指标/告警   │
│   · 先落库再 ack      · 退避重试              · 死信入队/重放    · outbox 发布 │
└────┬──────────────────────┬───────────────────────┬─────────────────────────┘
     │ Validate / BuildRequest │ 解析凭证             │ 读写状态事件
     ▼                        ▼                       ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ ③ 供应商适配层                                                               │
│   SupplierAdapter 接口                                                       │
│     ├ BaseSupplierAdapter (公共能力：通用校验 / 日志留存 / 请求脚手架)        │
│     └ CrmXAdapter   AdSystemAdapter   InventoryAdapter   …(每供应商一个)      │
│   SecretResolver (sops 后端，投递时解析 secret_ref → 真值)                   │
└────┬───────────────────────────────────────────────────────────────────────┘
     ▼
┌────────────────────────────────────────────────────────────────────────────┐
│ ④ 基础设施 / 存储层                                                          │
│   关系型 DB：notification(热表) │ notification(归档表) │ notification_event   │
│              │ supplier_config                                               │
│   MQ(状态事件分发)   sops(密钥)   离线 Hive(长期历史)   外部供应商 API(投递)  │
└────────────────────────────────────────────────────────────────────────────┘

  横切关注点（贯穿 ①~④）：日志 / 指标 / 告警 / 配置
```

**要点**：可靠性内核（②应用层）与供应商适配（③）解耦——适配类只做"该供应商的对接"（校验/组装/验签/响应/日志），HTTP 发送 / 重试 / 租约 / 2xx 判定一律归通用 worker。

## 二、数据架构

```
                          ┌──────────────────────────────────────────────┐
  提交 ─▶ 接收服务 ─写─▶  │ notification 【热表】(只存非终态)              │
                          │  id(=追踪ID) / idempotency_key / source_system │
                          │  type / params / status / attempts /          │
                          │  next_attempt_at / lease_owner / lease_until   │
                          └───────┬────────────────────────┬───────────────┘
  投递 worker 轮询领取 ◀──────────┘         到达终态(迁出)   ▼
  (只扫热表，始终快)                        ┌───────────────────────────────┐
                                            │ notification 【归档表】(终态)  │
  状态变更(同事务) │                         │  DELIVERED / DEAD，v1 暂不清理 │
                   ▼                         └──────────────┬────────────────┘
  ┌────────────────────────────────────┐                   │ 同步 (ETL)
  │ notification_event (状态历史+outbox) │                   ▼
  │  notification_id / from→to_status /  │            ┌──────────────┐
  │  coarse_status / attempt_no /        │            │ 离线 Hive 数仓│
  │  response_code / error / occurred_at │            │ (留几年)      │
  │  published_at (NULL = 待发布)        │            └──────────────┘
  └─────────┬───────────────────┬────────┘
            │ publisher relay     │ 支撑查询
            ▼ (粗三态)            ▼
      ┌──────────┐         业务方只读查询 / 运维 detail 查询
      │ MQ topic │ ─────▶  业务方按需订阅
      └──────────┘

  配置与密钥（投递时只读，不冻结进通知）：
  ┌─────────────────────────────────────┐    secret_ref    ┌───────────────┐
  │ supplier_config                      │ ───────────────▶│ sops 加密文件  │
  │  type / endpoint / method /          │   resolver 解析  │ (凭证真值)     │
  │  secret_ref / retry_policy / version │                  └───────────────┘
  └─────────────────────────────────────┘
```

**三条数据生命周期**：① 通知记录 热表(非终态) → 归档表(终态) → 离线 Hive；② 状态事件 同事务落 `notification_event`，经 outbox → MQ + 支撑查询；③ 配置只存 `secret_ref`，真值在 sops、投递时解析。请求体不落库，复盘靠适配类日志留存。

## 三、功能执行流程

```
【提交阶段】
业务系统 ──submit{idempotency_key, type, params}──▶ 接收服务
   │
   ├─ 幂等检查 (source_system, idempotency_key)
   │     └─ 命中 ─────────────────────▶ 返回【已有追踪ID】(不新建)
   │
   ├─ 适配类.Validate(params) ──校验失败──▶ 同步拒绝(不落库)
   │
   └─ 落库(status=PENDING, 仅存 params) + 写 event(ACCEPTED)
         └─────────────────────────────▶ 返回【唯一追踪ID (= notification id)】
                                           〔先落库再 ack = at-least-once 起点〕

【投递阶段】(投递 worker 循环)
轮询(带抖动) ─▶ 条件UPDATE领取(含过期租约) ─原子, attempts+1─▶ status=DELIVERING
   │
   ├─ 适配类.BuildRequest(params) + resolver 解析 secret_ref + 验签
   ├─ 通用 worker 发 HTTP (硬超时)
   └─ 适配类.HandleResponse + 日志留存
         │
         ├─ 2xx ─────────────────▶ DELIVERED ────────────┐
         │                                                 │
         ├─ 可重试(超时/5xx/429)                            │
         │     ├ attempts < max ─▶ 退避, 置 next_attempt_at ─▶ 回 PENDING
         │     └ attempts ≥ max ─▶ DEAD ──┐                │
         │                                 │                │
         ├─ 不可重试(4xx) ─────────▶ DEAD ─┤                │
         │                                 ▼                ▼
         └─ 崩溃 / 超 lease ─▶ 租约过期    〔DEAD: 告警〕  〔终态: 迁出热表 → 归档表〕
                              下轮被重领

【状态分发 & 查询 & 重放】
每次状态变更 ─同事务─▶ notification_event ─publisher─▶ MQ(粗三态) ─▶ 业务方订阅
业务方/运维 ─凭追踪ID查询─▶ 粗三态(默认) / detail(状态历史·重试·报错，受控)
运维 ─对 DEAD 发起重放─▶ params + 最新适配类重组 ─▶ 重新入队(PENDING)
```

**关键不变量**：at-least-once（先落库再 ack + 重试 + 租约兜崩溃）；2xx=送达（不解析业务语义）；终态迁出热表保证领取查询始终快；一次逻辑交互 = 一个稳定追踪 ID，贯穿查询与推送。

## 对齐说明

后续实现 tasks 应符合以上三图：

- **分层**：适配类不得承担传输/重试/租约（对应 `supplier-adaptation` 职责分离需求）。
- **数据**：请求体不落库、终态迁出热表、事件经 outbox 发 MQ（对应 `delivery-observability`）。
- **流程**：先落库再 ack、领取即 attempts+1、组装+验签在投递时、追踪 ID 贯穿全程（对应 `notification-ingestion` / `reliable-delivery` / `interaction-tracking-id`）。
