> 角色视角：中台研发架构师

> 决策来源与取舍论证：见 [方案决策记录.md](./方案决策记录.md)

## 1. 背景与需求

企业内部多个业务系统在关键事件发生时，需要调用外部系统供应商提供的 HTTPS API 进行通知。例如：

- 用户通过第三方广告系统引流并成功注册后，通知对应的广告系统；
- 用户订阅付款成功后，通知 CRM 系统更改 Contact 状态；
- 用户购买商品后，通知库存系统进行库存变更。

约束特征：

- 不同供应商的 API **请求地址不同、Header / Body 格式不同**；
- 业务系统**不关心外部 API 的返回值**，只需确保通知请求能被**稳定、可靠地送达**。

### 目标

设计并实现一个内部服务，接收业务系统提交的外部 HTTP 通知请求，并**尽可能可靠地投递到目标地址**。

---

## 2. 定位与核心价值

本系统是一个**出站通知可靠投递网关（Reliable Outbound Delivery Relay）**，采用**适配中心模式**：业务系统提交「通知类型 + 业务参数」，网关查供应商配置组装出真实 HTTP 请求并保证可靠送达。

```
   业务系统A ─┐                          ┌─▶ 广告系统 API
   业务系统B ─┼──▶ [ 通知系统 ] ─────────┼─▶ CRM 系统 API
   业务系统C ─┘     收下 + 保证送达       └─▶ 库存系统 API
                    (业务方 fire-and-forget)
```

核心价值：

1. **解耦故障域**——把「业务事务的完成」与「不可靠的外部网络调用」彻底分开。业务方提交即返回，重试 / 退避 / 兜底由网关承担。
2. **收敛对接知识**——把对接各供应商的格式、鉴权、签名知识从各业务系统收敛到平台一层，避免每个业务系统各自重复实现。

## 3. 系统边界

> 对应「设计说明要求 · 系统边界」：哪些问题在系统内解决？哪些明确不解决？为什么？

| ✅ 系统内解决 | ❌ 明确不解决 + 理由 |
|---|---|
| 通知的**可靠投递**（持久化 + 重试 + 兜底） | 外部 API 的**业务语义**——需求明确「业务方不关心返回值」，故只认 HTTP 传输层结果（2xx = 送达），不解析 body |
| 提交侧**幂等去重**（防业务方重复提交） | 请求体的**自由转换 / 编排引擎**——请求组装由适配类代码承载，v1 不引入模板引擎 |
| 供应商**对接适配**（每供应商一个适配类：校验/组装/验签/响应/日志） | **exactly-once**——跨网络不现实，提供 at-least-once + 下游幂等 |
| 故障**隔离**（坏供应商不拖垮全局投递） | **有序投递**——通知事件相互独立，v1 不保证顺序 |
| 投递**状态可查** + 状态事件分发 | 业务侧**本地事务原子性**——属于业务方 outbox 职责，在本系统边界之外 |

## 4. 核心能力拆分

系统是一条流水线，每个环节对应一项可靠性责任：

```
┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐
│① 接收  │─▶│② 持久化│─▶│③ 投递  │─▶│④ 重试  │─▶│⑤ 兜底  │  │⓪ 适配  │
│ Accept │  │Persist │  │Dispatch│  │ Retry  │  │  DLQ   │  │Adapter │
└────────┘  └────────┘  └────────┘  └────────┘  └────────┘  └────────┘
 幂等+校验   落库才返回   组装+验签   退避+上限    死信+告警   每供应商
 +快速ack    =at-least-once +发HTTP认2xx 熔断隔离   重放入口    一个类
                            ⑥ 可观测：状态查询 / MQ事件 / 指标 / 日志（贯穿全程）
  ⓪ 适配类贯穿 ①(校验) 与 ③(组装+验签+响应+日志)，不参与传输/重试/租约
```

| 环节 | 职责 | 关键设计点 |
|------|------|-----------|
| ⓪ 适配 | 供应商适配类据 type 选定、据 params 组装请求 | 每供应商一个适配类，v1 不引入模板引擎 |
| ① 接收 | 业务系统提交 API | **幂等键**去重；适配类做必须参数校验；**先落库再 ack** |
| ② 持久化 | 待投递通知落到可靠存储 | v1 用 DB 表当队列；仅存原始 params |
| ③ 投递 | worker 调适配类组装+验签后发起对外 HTTP 调用 | 凭证晚绑定、签名现算；只认 2xx = 送达 |
| ④ 重试 | 失败后按退避策略重投 | 指数退避 + 抖动；明确可重试状态码 |
| ⑤ 兜底 | 重试耗尽后进死信 | 告警 + 人工介入 + 重放（用 params + 最新适配类重组） |
| ⑥ 可观测 | 状态查询 / MQ 事件 / 指标 | 粗三态对业务方，detail 给运维 |

> **核心洞察**：可靠性内核（持久化 / 重试 / 熔断 / 死信）与适配方式无关。供应商适配收敛在「每供应商一个适配类」里（接收时校验、投递时组装+验签+响应+日志），复杂度被关在适配类内，不污染投递核心。

## 5. 核心设计决策概览

完整论证见 [方案决策记录.md](./方案决策记录.md)，此处摘要：

| # | 决策 | 选择 | 一句话理由 |
|---|------|------|-----------|
| 一 | 网关定位 | **适配中心(B)** | 把供应商对接知识收敛到平台一层（中台定位） |
| 二 | 组装时机 | **接收校验 + 投递组装**（v1 不引入模板、不冻结请求） | 无模板更简单；复盘靠适配类日志留存，死信用 params + 最新适配类重组 |
| 三 | 任务领取 | **DB 当队列 + 租约 + reaper 折叠 + 领取即 +1** | v1 量级够用、可调试；租约兜住崩溃，防毒丸 |
| 四 | 供应商适配 | **每供应商一个适配类 + 基础类沉淀公共能力 + 凭证晚绑定(sops)** | 对接(尤其验签)高度异构，靠代码多态而非配置；签名带时间戳须现算 |
| 五 | 状态回查 | **只读拉取 + MQ outbox + 分层保留** | pub/sub 扇出不反向耦合；outbox 不丢事件 |

另有一条「评估过但未采纳：Redis 分布式锁」——对应作业要求的「识别过度设计」。

## 6. 数据模型

```
notification
├ id                 系统生成 (ULID)
├ idempotency_key    (source_system, key) 唯一 → 幂等去重
├ source_system      来源业务系统
├ type               通知类型 → 映射 supplier_config
├ params             原始业务入参 (JSON)；投递时由供应商适配类据此组装请求，死信重放复用
├ status             PENDING / DELIVERING / DELIVERED / RETRYING / DEAD
├ attempts / max_attempts
├ next_attempt_at    下次可投递时间（退避调度）
├ lease_owner / lease_until   worker 租约，防重复领取
├ last_error / last_response_code
└ created_at / updated_at

notification_event   ← 状态历史表 + MQ outbox（一表两用）
├ id / notification_id
├ from_status / to_status / coarse_status   粗三态：ACCEPTED/DELIVERED/FAILED
├ attempt_no / response_code / error
├ occurred_at
└ published_at        relay 到 MQ 的时间（NULL=待发，支撑 outbox 补发）

supplier_config       连接与凭证信息（请求组装逻辑在适配类代码里，不在配置）
├ type (或 supplier id)
├ endpoint / method
├ auth                凭证引用（secret_ref，不存真值）
├ retry_policy        {max_attempts, backoff_base, backoff_max, retryable_codes}
└ version
```

> v1 不引入模板引擎：请求组装、验签、响应处理、日志留存均由**每供应商一个适配类**（继承基础类）以代码实现，`supplier_config` 仅存连接与凭证引用。

## 7. 关键流程

### 7.1 接收（Accept）

业务方提交 `{idempotency_key, type, params}`：

1. 按 `(source_system, idempotency_key)` 幂等去重；
2. 调用对应供应商适配类的 `Validate` 对必须参数做 **fail-fast 校验**；
3. **先落库再返回 ack**（落库即 at-least-once 起点，仅存原始 `params`，不冻结请求），同时写一条 `ACCEPTED` 的 `notification_event`，并返回唯一追踪 ID。

### 7.2 组装时机：接收校验 + 投递组装（决策二）

```
提交(accept) 时： 适配类.Validate(params) 必须参数 fail-fast + 存原始 params
投递(deliver)时： 适配类.BuildRequest(params) 据入参组装请求
                  + resolve(secret_ref) + 验签(时间戳/nonce/签名) → 发送
```

v1 不引入模板引擎、不冻结请求；复盘性由适配类**日志留存**（记录实际发出的请求/响应）承接。死信重放用保留的 `params` + 最新适配类重新组装（抢救供应商改对接的场景）。

### 7.3 任务领取与投递（决策三）

```
轮询(带抖动) ─▶ 条件UPDATE批量领取(含过期租约) ─原子+attempts─▶ DELIVERING(lease=30s)
                  │ 适配类据 params 组装请求+验签
                  ▼
                发HTTP(硬超时10s)
                  ├─ 2xx ─▶ DELIVERED
                  └─ 失败/崩溃 ─┬─ attempts<max ─▶ 回PENDING+置next_attempt_at
                                └─ attempts≥max ─▶ DEAD   (崩溃则靠租约过期被重领)
```

- **领取**：带条件原子 UPDATE 抢占租约，DB 行锁保证不重复领取；领取查询直接把「过期租约的 DELIVERING」纳入可领对象，无需独立 reaper 进程。
- **租约**：固定 30s（> HTTP 硬超时 + 余量），单任务有界故不做心跳续租。
- **attempts**：领取即 +1，防毒丸任务无限循环。

### 7.4 供应商适配类（决策四）

```
SupplierAdapter 接口  ←─ 每供应商一个实现类，公共能力下沉 BaseSupplierAdapter
├ Validate(params)        必须参数校验（接收时 fail-fast 调）
├ BuildRequest(params)    据入参组装请求 + 验签（投递时调，凭证由 resolver 解析）
├ HandleResponse(resp)    响应处理
└ (日志留存)              留存实际请求/响应供复盘

通用 worker：HTTP 发送 + 重试 + 租约 + 2xx 判定（供应商无关，不进适配类）
```

- 凭证只存 `secret_ref`，投递时由 resolver 解析（v1 后端用 sops 加密配置文件）供适配类使用。
- 各供应商对接（尤其验签）高度异构 → 用代码适配类（多态），不做配置驱动的通用签名/模板引擎；公共能力（通用校验、日志）下沉基础类。
- 代价：每接入一个供应商需一个适配类（简单的薄层继承基础类），放弃纯配置零代码接入。

### 7.5 状态回查与可观测（决策五）

```
状态变更 ──同一DB事务写──▶ notification_event (状态历史 / outbox)
                              ├─ 支撑 ─▶ 只读查询 detail 模式
                              └─ relay ─▶ publisher ─▶ MQ topic ─▶ 业务方按需订阅(粗三态)
```

- 运维侧（必做）：查询 / 列 DEAD / 手动重放 / DEAD 告警 / 指标。
- 业务方（可选）：只读拉取 + MQ 事件订阅双通道做异步对账，不鼓励同步等待。
- MQ 仅用于状态事件分发（pub/sub 扇出，不反向耦合）；outbox 保证不丢事件，MQ 未就绪时表本身即完整记录。
- 粒度：MQ 只发粗三态；只读查询默认粗三态，`detail` 参数（限运维/特权方）返回历史/重试次数/报错。

## 8. 可靠性与失败处理

> 对应「设计说明要求 · 可靠性与失败处理」：投递语义是什么？外部失败 / 长期不可用如何处理？

### 状态机

```
 accept(校验✓) ─▶ PENDING ─worker领lease─▶ DELIVERING(适配类组装+验签) ─2xx─▶ DELIVERED(终态)
                                                     │
                       可重试(超时/5xx/429)          │ 不可重试(400/401/403)
                    ┌────────────────────────────────┴──────────┐
                    ▼                                             ▼
                 RETRYING ─(attempts<max, 等 backoff)─▶ 回 PENDING  DEAD(终态)
                    └─ attempts ≥ max ─▶ DEAD(终态) ─params+最新适配类重组─▶ 重新入队
```

### 投递语义：**at-least-once**

要「保证送达」就必须重试；重试必然带来重复；exactly-once 跨网络不现实。→ 选 at-least-once，并把**幂等责任下推给外部接口**（或我们带幂等键过去）。

### 失败分类与处理

- **可重试**：超时 / 连接重置 / 5xx / 429 → 指数退避 + 抖动重投。
- **不可重试**：400 / 401 / 403 等确定性失败 → 不盲目重试，直接进死信等人工（401/403 多为凭证/签名配置错）。
- **外部长期不可用**：
  - 退避封顶；达 `max_attempts` 进死信队列 + 告警；
  - 对单供应商**熔断** + **并发隔离**，避免 worker 全耗在死端点、饿死健康供应商；
  - 死信支持人工 / 改配置后重渲染重放。

## 9. 取舍与「过度设计」清单

> 对应「设计说明要求 · 取舍与演进」：哪些 AI 方案建议是「过度的」，不予采纳？

| 不采纳的方案 | v1 替代 | 理由 |
|---|---|---|
| 模板 / 脚本引擎做请求组装（含 `{{var}}` 插值、Jsonnet） | 每供应商一个代码适配类（基础类沉淀公共能力） | 各供应商对接异构，v1 用代码更直接；公共能力靠基础类复用 |
| 直接上 Kafka 做投递队列 | DB 表当队列 + 轮询 + 租约领取 | v1 量级够用、可调试性强（延迟队列靠 `next_attempt_at` 免费拿到） |
| **Redis 分布式锁**（worker 领取） | DB 条件 UPDATE + 租约 + reaper | 领取去重 DB 已原子解决；处理重复 Redis 锁与租约同种 TTL 失效，且外部 API 无法校验 fencing token，补不齐 |
| 配置驱动的通用签名引擎 | 适配类代码现算验签 | 各供应商验签规范异构，一套 schema 越兜越大且漏抽象 |
| webhook 逐个推送业务方 | MQ 事件订阅（pub/sub） | webhook 会让我方递归造一套可靠投递 |
| 配置中心 UI / 审批流 | `supplier_config` 表 + admin API | 避免过早治理投入 |
| 业务↔网关分布式事务（2PC/Saga） | 持久化 accept + 调用方重试幂等 | 边界清晰，复杂度更低 |

## 10. 演进路线

> 对应「设计说明要求 · 取舍与演进」：流量 / 复杂度增长时如何演进？

```
 v1 (MVP)                             增长后
 ┌──────────────────────┐           ┌──────────────────────────┐
 │ 单服务               │           │ 接入层 / worker 水平扩展  │
 │ DB 表当队列+轮询+租约 │   ───▶    │ 投递队列换真·MQ           │
 │ 简单退避重试+熔断     │           │ 延迟队列 + 死信队列       │
 │ MQ 仅做状态事件分发   │           │ 按供应商分片 / 隔离 / 限流│
 │ 归档表+离线Hive       │           │ 熔断 + 多副本             │
 └──────────────────────┘           └──────────────────────────┘
```

判断依据：v1 量不大时，一张表 + 状态机 + 轮询就能给到 at-least-once，比直接上 Kafka 简单、可调试性强；等吞吐 / 解耦压力（热点行争用、轮询延迟无法接受）真正出现，再把投递队列换 MQ。归档表无界增长由离线 Hive 长期承接。

## 11. 开源中间件选型说明

> 对应「其他说明」：使用开源中间件须说明为什么选、不使用时的替代方案。

| 中间件 | 用途 | 为什么选 | 不使用时的替代 |
|---|---|---|---|
| 关系型数据库（MySQL/PG） | 持久化 + 当投递队列 | 已有基础设施；事务 + 行锁天然给到原子领取与 at-least-once；`next_attempt_at` 即延迟队列 | 无替代——持久化是可靠投递的底座 |
| 消息队列（MQ） | **仅**状态事件分发（pub/sub） | 扇出 / 多订阅者 / 与业务方解耦，且不反向耦合 | 退化为仅 outbox 表 + 只读查询，业务方改用轮询拉取 |
| sops | 凭证加密存储 | 文件加密 + git 管理，与配置即代码同源，v1 够用 | 环境变量 / 加密 DB 列；resolver 抽象已留好，后换 Vault/KMS 零侵入 |

> 投递工作队列**不**用 MQ：租约 / 重试 / 延迟语义在 DB 上更顺手；MQ 仅承担状态分发，两个关注点分开。

## 12. 待细化项（进入实现时）

- MQ 选型（RocketMQ / Kafka / 其他）与 topic 划分。
- 归档表迁移触发方式（定时任务 / 状态流转时同步）与离线 Hive 同步管道。
- 幂等键作用域与冲突返回语义（同 key 重复提交时返回已有 id 还是报错）。
- 单供应商熔断 / 并发隔离的具体参数（阈值、半开探测、每供应商并发上限）。
