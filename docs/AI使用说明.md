# AI 使用说明

本作业在 AI（Claude Code）辅助下完成。下面如实说明 AI 在哪些地方提供了帮助、哪些 AI 建议**未被采纳**、以及哪些关键决策是我自己做出的及其原因。整个过程的取舍轨迹也保留在 [`docs/方案决策记录.md`](方案决策记录.md) 中。

---

## 一、AI 在哪些关键地方提供了帮助

1. **需求拆解与边界界定**：把"调用外部 API 通知"抽象为"出站通知可靠投递网关"，拆出接收 / 持久化 / 投递 / 重试 / 兜底 / 可观测的能力流水线，并列出"明确不做"的边界。
2. **设计论证**：补全 at-least-once 语义、状态机、退避/熔断/死信策略；尤其在"Redis 分布式锁能否解决领取重复"上给出了完整论证（DB 条件 UPDATE 已原子去重；锁与租约同种 TTL 失效；外部 API 无法校验 fencing token）。
3. **代码实现**：生成 Go + Echo + SQLite 的 MVP 骨架与各模块（接收、租约领取、适配类、outbox、查询），以及单测 / 集成测试 / 端到端脚本。
4. **排障**：定位端到端冒烟"Empty reply"实为本机 SOCKS 代理所致（非代码问题），而非服务缺陷。
5. **文档产出**：需求分析、决策记录、三张架构图、本说明的初稿。

## 二、AI 给出过、但我没有采纳的建议

1. **网关定位**：AI 倾向先推"透明中继（业务方传完整 HTTP 请求）"作为最简方案。我改选**适配中心**——把供应商对接知识收敛到平台一层，更符合中台定位。
2. **请求组装方式**：AI 设计了"`{{var}}` 模板 + 提交时渲染并冻结 rendered_request"的混合方案。我**取消模板引擎**，改为**每供应商一个代码适配类**，理由见下。
3. **验签抽象**：AI 一度建议"闭集泛化的签名 strategy + 配置选择（alg/sign_headers 等）"。我不认可——各下游验签规范差异巨大，配置 schema 越兜越大且漏抽象，应**用代码多态**（每个下游一个类）实现。AI 随后认同此判断。
4. **凭证后端**：AI 推荐用环境变量做 v1 的 secret resolver 后端。我改用**本地加密配置文件（sops 风格）**，与"配置即代码"同源。
5. **简单供应商接入**：AI 设想"DefaultBearerAdapter 纯配置零代码接入简单下游"。在我确定"每供应商一个类"后这一设想被放弃（简单下游改为薄层继承基础类）。

## 三、哪些关键决策是我自己做出的，以及原因

1. **适配中心模式**：业务方只提交 `type + params`，由网关组装。原因：收敛对接知识、避免各业务系统重复实现重试与对接。
2. **取消模板、每供应商一个代码适配类**：适配类包揽必须参数校验、请求组装 + 验签、响应处理、日志留存；公共能力下沉基础类。原因：验签高度异构、必须现算（带时间戳/nonce），代码比配置更直接可测；用多态拿"通用"。代价（每接入一个供应商需改代码发版）我接受。
3. **不在 accept 冻结请求**：仅做必须参数 fail-fast 校验、存原始 `params`；组装/验签延后到投递时。复盘性改由适配类**日志留存**承接。原因：没有模板就无需冻结，且签名本就不能冻结。
4. **状态回查走"只读拉取 + MQ outbox 订阅"**：而非 webhook 逐个推送。原因：pub/sub 扇出不反向耦合业务方；outbox 保证不丢事件且 MQ 非阻塞依赖。这一双通道是我主动加的（AI 原先更倾向"仅运维可查 + 只读"）。
5. **新增唯一交互追踪 ID**：提交即返回稳定唯一 ID（复用 notification id），幂等重提返回同一 ID，查询与推送统一以它关联。原因：方便业务方追踪一次逻辑交互的全生命周期。
6. **技术栈与框架约束**：选 Go + 轻量可跑依赖（SQLite 当库当队列、进程内 MQ），并明确要求 **HTTP 接入层用 Echo 框架**。原因：贴合作业"MVP、不要求生产级"，同时统一接入层写法。
7. **主动管理复杂度（拒绝过度设计）**：不引入 Redis 分布式锁、配置驱动通用签名引擎、Kafka 投递队列、Vault、exactly-once。原因：各自要么在本场景冗余、要么补不齐、要么 v1 过重；抽象（Resolver / MQ / 适配接口）保留以便后续替换。

---

> 一句话总结：AI 加速了分析、论证、编码与文档，但**系统边界、适配方式、复杂度取舍、框架与能力约束等关键工程决策由我做出**，并在多处修正了 AI 的初始建议。
