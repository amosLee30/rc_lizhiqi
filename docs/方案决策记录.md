## 决策一：网关定位 —— 透明中继 vs 适配中心

**问题**：通知系统对「供应商格式差异」的处理边界是什么？这决定整个数据模型和复杂度。

| 候选方案 | 含义 | 是否采纳 |
|---|---|---|
| A · 透明中继 | 调用方提交已构造好的完整 HTTP 请求（url/method/header/body），网关只负责可靠投递、不碰内容 | ❌ |
| **B · 适配中心** | 网关存供应商配置（endpoint + header/body 模板），调用方只传「通知类型 + 业务参数」，由网关组装请求 | ✅ **已选** |
| A + 轻配置 | 以透明中继为底座，仅把鉴权/签名等少数公共能力做成可选凭证配置 | ❌ |

**最终选择**：**B · 适配中心**

**理由**：
- 更贴合「中台」定位——把对接各供应商的格式知识从各业务系统**收敛到平台一层**，避免每个业务系统各自实现重试与对接。

**已识别的代价 / 风险**：
- B 把「过度设计风险」从『要不要做』搬到了『做多狠』——必须主动约束模板引擎的复杂度（见决策三的延伸约束）。
- 新增「组装层 + 配置仓库」两块责任：配置管理、模板渲染、类型注册、参数校验。

**关键洞察**：可靠性内核（持久化/重试/熔断/死信）与 A/B 选型无关。B = A + 组装层 + 配置存储，复杂度可被关在组装层内，不污染投递核心。

## 决策二：渲染时机 —— 提交时冻结 vs 投递时渲染

> **⚠️ v1 简化修订（后续）**：在决策四把适配收敛到「每供应商一个代码适配类」后，**v1 取消模板引擎**，本决策随之简化为「**接收时校验 + 投递时由适配类组装（不冻结请求）**」：
> - accept 时：调用适配类 `Validate(params)` 做必须参数 fail-fast，仅存原始 `params`；
> - deliver 时：适配类 `BuildRequest(params)` 据入参组装请求 + 验签；
> - 复盘性改由适配类**日志留存**（记录实际发出的请求/响应）承接，不再保留 `rendered_request` 列；
> - 死信重放用 `params` + 最新适配类重组。
>
> 下方原始探讨（模板 + 混合冻结）保留作复盘，记录"先选混合、后因取消模板而简化"的演进。

**问题**：选了适配中心后，「什么时候把 type+params 渲染成真实 HTTP 请求」决定了数据模型与故障恢复能力。

| 候选方案 | 优点 | 缺点 | 是否采纳 |
|---|---|---|---|
| 提交时冻结 | accept 即可 fail-fast 校验；投递层退化成透明中继、极简；存的就是发出去的、可复盘 | 配置变更救不回在途/死信通知 | ❌ |
| **混合** | 上述优点 + 死信时可用新配置重新渲染再重放 | 多存一份原始入参 | ✅ **已选** |
| 投递时渲染 | 改配置能救活卡住的通知 | accept 无法 fail-fast；模板 bug 大面积潜伏、发现晚；存的≠发的、难复盘 | ❌ |

**最终选择**：**混合**

**理由**：
- 兼得「正常路径极简、可复盘」与「故障可抢救」两边的好处，代价仅为多存一份入参。

**落地体现**：数据模型中**同时保留** `rendered_request`（提交时渲染冻结，正常路径重放）与 `params`（原始入参，死信时用新配置重渲染）。

## 决策三：任务领取机制（DB 表当队列下的细节）

**前提**：MVP 用 DB 表当队列 + 轮询 + 租约领取（已排除 Redis 锁，见「评估过但未采纳」）。以下四个细节决定行为正确性，均已确认。

### 3.1 Lease 时长：固定租约，不做心跳续租

- 关键性质：**每条任务就是一次有界的 HTTP 调用**。
- 做法：给 HTTP client 设硬超时（如 10s），`lease = 超时 + 余量`（如 30s），恒大于单次任务上界。
- 因此**不需要心跳续租**，省掉「续租定时器 + 失败处理」一块复杂度。
- 演进信号：将来若出现批量/长任务，再引入续租。

### 3.2 Reaper 折叠进领取查询（v1 不起独立 reaper 进程）

领取查询直接把「过期租约的 DELIVERING」视为可领对象：

```sql
WHERE next_attempt_at <= now()
  AND ( status='PENDING'
        OR (status='DELIVERING' AND lease_until < now()) )
```

- 崩溃任务在下次有 worker 轮询时自然被重领，**零额外组件**。
- 代价：过期任务要等下一次轮询、崩溃率不好单独统计。
- 演进信号：需要崩溃率指标、或想缩短崩溃后重试延迟时，再拆出独立 reaper。

### 3.3 attempts 计数：领取（转 DELIVERING）时即 +1

- 若「出结果后」才 +1：毒丸任务每次一领到就崩 → attempts 加不上去 → 永不到 max → 无限循环、毒死 worker。
- 故选**领取即 +1**，语义为「max_attempts = 最多领取投递次数（含崩溃）」。
- 代价：我方一次网络抖动也消耗一次预算——但这是安全方向（宁可早进死信告警，也不要无限循环）。

### 3.4 批量领取 + 热点行防护

- **批量**：一次 `LIMIT N` 领 N 条减少往返；N 越大、单 worker 崩溃冻住的任务越多 → 取中等批量（10～50），按吞吐调。
- **争用**：必备 `(status, next_attempt_at)` 复合索引；轮询加**抖动**防同步惊群；抢不到的 worker `affected_rows` 少、下轮再领，不会错乱。

### 领取生命周期

```
轮询(带抖动) ─▶ 条件UPDATE批量领取(含过期租约) ─原子+attempts─▶ DELIVERING(lease=30s)
                                                                      │
                          ┌──────────── 发HTTP(硬超时10s) ────────────┤
                          ▼                                            ▼
                       2xx: DELIVERED                          失败/崩溃
                                                    ┌───────────┴────────────┐
                                              attempts<max               attempts≥max
                                          回PENDING+置next_attempt_at        DEAD
                                          (崩溃则靠租约过期被重领)
```

## 决策四：供应商适配 —— 每供应商一个适配类（含凭证与验签）

> **⚠️ v1 简化修订（后续）**：本决策最初聚焦"凭证 + per-downstream 验签适配类"。后续将适配类职责**从"只管验签"扩大到"该供应商的全部对接"**，并**取消模板引擎**：
> - 抽象 `SupplierAdapter` 接口，**每供应商一个实现类**，承载：必须参数校验（`Validate`，接收时调）/ 请求组装 + 验签（`BuildRequest`，投递时调）/ 响应处理（`HandleResponse`）/ 日志留存；
> - **公共能力下沉 `BaseSupplierAdapter` 基础类**（通用参数校验、日志、请求脚手架），简单供应商薄层继承；
> - 凭证仍只存 `secret_ref`、投递时由 resolver 解析（sops 后端）供适配类使用；
> - **代价**：每接入一个供应商都需一个适配类，放弃"纯配置零代码接入简单下游"（原 DefaultBearerAdapter 纯配置接入的设想不再适用），换 v1 简单直接。
>
> 下方 4.1~4.5 原始探讨（auth 与 rendered_request 正交、冻结语义收窄、DefaultBearerAdapter 纯配置接入等）保留作复盘；其中"验签用代码适配类、不做配置驱动签名引擎"的核心判断不变，只是适配类的职责范围扩大、且不再有模板与冻结请求。

**问题**：供应商鉴权凭证怎么管？验签方式各下游不一致怎么适配？凭证与「提交时冻结」如何共存？

### 4.1 auth 与 rendered_request 正交，凭证晚绑定

- auth **不塞进** rendered_request；冻结的请求**天生不含密钥、不含签名**。
- 凭证投递时由 resolver 解析（`secret_ref → 真值`），鉴权/签名投递时独立施加。
- 收益：「存的请求不含密钥」从安全负担变成安全特性，审计/脱敏天然干净。

### 4.2 「冻结」语义收窄

```
提交(accept) 时： 校验变量 + 冻结【业务骨架】
                  = url / method / 业务 body / 非密 headers
投递(deliver)时： ① resolve(secret_ref) 取真值
                  ② 加工验签字段(timestamp / nonce / signature)
                  ③ 施加 auth / 注入签名头
```

理由：HMAC 的时间戳/nonce 一旦冻结即过期，签名**必须现算**，故只冻业务语义部分。

### 4.3 验签：per-downstream 适配类（代码），不做配置驱动通用签名引擎

- **不采纳**「配置驱动的通用 HMAC 引擎」（`{alg, sign_headers, canonicalization...}`）：
  AWS SigV4 / 支付宝 / 微信 / Stripe 的规范化、签哪些字段、编码、签名串拼法各不相同，
  一套 config schema 越兜越大且总不贴合 = 漏抽象。
- **采纳**：每个下游用自己的适配类（代码）实现签名/鉴权，靠多态拿"通用"，而非堆配置参数。
- 额外收益：适配类的 `Sign` 方法可用供应商文档的测试向量直接单测，配置引擎做不到。

```
配置(sops): supplier_config = { supplier_id, endpoint, secret_ref, 非密参数 }
            ← 只存密钥引用与连接信息，不含任何签名逻辑

代码侧: DownstreamAdapter 接口 (统一 sign/apply 入口)
        ├ CrmXAdapter.Sign(req, secrets)
        ├ AdSystemAdapter.Sign(req, secrets)
        └ DefaultBearerAdapter            ← 简单静态 token 的下游共用，免新类

投递时(通用 worker)：
  取 rendered_request(业务骨架) + resolve(secret_ref)
    └▶ 按 supplier 选 Adapter
    └▶ adapter.Sign(req, secrets)   ← 各下游验签现算、注入签名/鉴权头
    └▶ 通用 worker 发 HTTP + 重试/租约   ← 下游无关，不进适配类
```

### 4.4 边界（已确认）

1. **适配类只负责"把请求签好/鉴权好"**（贡献签名与 auth 头）；
   **HTTP 发送 + 重试 + 租约仍归通用 worker**，每个下游类不重写传输与可靠性。
2. **简单静态 token 的下游不必新建类**，共用 `DefaultBearerAdapter`、纯配置接入；
   只有验签/鉴权有特殊规范的下游才写专属适配类。

### 4.5 Resolver 后端：本地配置文件（sops）

- 文件加密 + git 管理，与「配置即代码」同源，适合 v1。
- 代价：**轮换密钥要重新部署/重载**；`resolver` 抽象已留好，轮换频繁时换 Vault（热更新）零侵入。
- 401/403 在 v1 → DEAD + 告警（静态 key 配错）；将来 OAuth 适配类内部做"刷新一次再试"。

**原则一致性**：能配置的配置（body 字段填充用 `{{var}}`），该写代码的写代码（验签/特殊鉴权用适配类）——与否掉模板 DSL 同一条线：别把逻辑硬塞进配置。

**代价（已接受）**：新接一个"有特殊验签"的下游 = 改代码 + 发版；简单静态鉴权下游仍纯配置接入。

## 决策五：状态回查与可观测

**问题**：投递状态对谁开放、开放到什么程度？终态数据怎么存？

### 5.1 先分两类消费者

- **运维/平台（必做）**：查 by id/key、列 DEAD、手动重放、DEAD 告警、指标。
  这不是"状态回查"的可选项，而是死信兜底本就欠的债——没有它死信队列 = 黑洞。
- **业务方（可选）**：偶尔做对账，回答"那条到底送没送到"。
  风险：给了查询业务方容易写成 `submit→轮询到 DELIVERED` 的同步等待，把解耦又焊回去。

### 5.2 业务方拿结果：只读拉取 + MQ 事件订阅（双通道）

- **拉取**：accept 返回 id，业务方按需查询做异步对账。
- **MQ 事件订阅**：状态事件 publish 到 topic，业务方 opt-in 订阅。
- **为何不是 webhook 推送**：webhook 要我方逐个 POST 业务端点、对每个端点保证可靠投递 = 递归造一套通知系统；
  而 MQ 是 pub/sub 扇出，扇出/重投归 MQ、业务方自行订阅，不反向耦合。

### 5.3 用事务性 outbox 衔接 MQ（v1 引入 MQ，仅用于状态事件分发）

- 与决策三"投递队列用 DB 当队列、不上 Kafka"**不矛盾**——两个关注点分开：
  - 投递工作队列：需要租约/重试/`next_attempt_at` 延迟语义 → DB 当队列更顺手（保留）。
  - 状态事件分发：需要扇出/多订阅者/解耦 → MQ pub/sub 更顺手（新增）。

```
状态变更 ──同一DB事务写──▶ notification_event (状态历史表 / outbox)
                              ├─ 支撑 ─▶ 只读查询 detail 模式(历史/重试次数/报错)
                              └─ relay ─▶ publisher ─▶ MQ topic ─▶ 业务方按需订阅(粗三态)
```

- **一张 `notification_event` 表干两件事**：既是只读查询 detail 模式的数据源，又是发 MQ 的 outbox。
- 状态事件先落库再发 MQ → 不丢事件；MQ 临时挂了 publisher 恢复后补发。
- 即便 v1 MQ 未接好，outbox 表本身就是完整记录、查询照常工作 → **MQ 是锦上添花的下游，非阻塞项**。

### 5.4 状态粒度：粗三态默认 + detail 参数 + 访问控制

- **MQ 事件**：只发粗三态（至少终态 DELIVERED/FAILED，ACCEPTED 可选）。
- **只读查询**：`detail` 参数控制——默认粗三态（`ACCEPTED/DELIVERED/FAILED`）；
  detail 模式返回状态变更历史 / 时间 / 重试次数 / 报错原因。
- **访问控制**：detail 模式仅运维/特权方可见，业务方默认拿粗三态——
  防内部状态机细节变成对外契约、也抑制紧轮询。

粗三态映射：`PENDING/DELIVERING/RETRYING → ACCEPTED`，`DELIVERED → DELIVERED`，`DEAD → FAILED`。

### 5.5 终态分层保留

```
热表(只存非终态)──终态迁出──▶ 归档表(在线,终态)──同步──▶ 离线Hive(数仓)
轮询领取只扫热表,始终快        暂不清理,始终保留          留几年,满足业务长期诉求
                              对账/查询走归档表
```

- 终态迁出热表，保证决策三的领取查询只扫非终态、始终快。
- 归档表 v1 **暂不清理**（始终保留）；后续建离线 Hive 表做长期历史（留几年）。
- **长期隐患（未来项）**：归档表"暂不清理"会无界增长；缓解阀门是离线 Hive——
  待离线同步建好，归档表可反过来设上限（数据已安全落 Hive）。

## 评估过但未采纳

### Redis 分布式锁（用于 worker 任务领取）

**提议**：在 worker 领取任务时引入 Redis 分布式锁，避免并发导致的领取重复（拟与租约+reaper 配合）。

**结论：不采纳——冗余且补不齐。**

理由：

1. **「领取重复」DB 已原子解决**：租约领取是一条带条件的原子 UPDATE
   （`UPDATE ... SET lease=... WHERE id=:id AND status='PENDING'`），
   DB 行锁保证 N 个 worker 抢同一行只有 1 个 `affected_rows=1`。
   Redis 锁是在 DB 已能原子仲裁的事情上再叠一层协调系统，多一次网络往返、多一个故障源，安全性没有增加。

2. **「处理重复」Redis 锁和租约是同一种失效**：worker 领到后发 HTTP，
   若 GC 停顿/慢调用导致 TTL 到期，另一 worker 会领到同一条、两次投递。
   Redis 锁 TTL 到期与租约 TTL 到期是**完全相同的失效模式**，只是把窟窿从 DB 挪到 Redis。
   带超时的锁无法给出 exactly-once。

3. **fencing token 在本场景补不齐**：要让分布式锁真正安全，需被保护资源校验 fencing token；
   但我们要保护的是**外部供应商 API**，不归我们管、不会校验任何 token，这条路根本走不通。

**因此**：领取去重靠 DB 条件 UPDATE；崩溃回收靠 reaper 退回过期租约；
重复投递靠 **at-least-once + 下游幂等**（设计上已接受）。三件事 Redis 锁都没新增保证，只增加组件与「两个 TTL 计时器互相作用」的推理负担。

**Redis 真正该上的时机**：不是作为「DB 之上的锁」，而是作为**队列本身**——当 DB 轮询吞吐/热点行争用到瓶颈时，用 Redis Streams / MQ 替换「DB 当队列」这一层（演进阶段的角色替换，非 v1 叠锁）。
